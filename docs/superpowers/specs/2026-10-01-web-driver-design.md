# Драйвер `web` для grok-imagine-mcp: Grok Imagine через окно Chrome, без API-ключа

Дата: 2026-10-01. Статус: черновик на проверку владельцем. Код не написан.

## 1. Цель

Claude Code и Codex ставят задачи Grok Imagine (видео по тексту, видео по фото, картинка по тексту) через уже
существующие MCP-инструменты и получают готовый файл на диске. Генерация идёт **по подписке пользователя, без
`XAI_API_KEY`**: драйвер управляет веб-интерфейсом `https://grok.com/imagine` в отдельном окне Chrome.

Критерий готовности: из Claude Code и из Codex вызов `grok_generate_video` (с фото и без) и затем
`grok_task_status` возвращает путь к целому mp4-файлу в `GROK_OUTPUT_DIR`.

Допущения (подтверждены владельцем в диалоге): один аккаунт и один профиль Chrome; генерации идут по одной, остальные
ждут в очереди; окно Chrome видимое (не headless); API-драйвер `xai` остаётся как есть; набор из пяти инструментов
не меняется.

## 2. Вне рамок

Headless-режим; несколько аккаунтов; параллельные генерации; Edge и Firefox; автоматический вход в аккаунт;
шаблоны Imagine («Reimagine», «Photo Edit» и т. д.), «Новый холст», «Агент»; склейка видео и список медиа из старого
прототипа `MCP_Grok_claude_codex`.

## 3. Что подтверждено пробой на машине владельца

Проба выполнена 2026-09-30/10-01 на Chrome 154, Windows 11, интерфейс на русском. Сгенерировано одно тестовое видео.

| Вопрос | Результат |
|---|---|
| Чем является «десктоп-приложение Grok» | Веб-приложение Chrome (`chrome_proxy.exe --profile-directory=Default --app-id=…`). Отдельного `.exe` нет |
| Можно ли управлять им как есть | Нет: профиль по умолчанию, без порта отладки; Chrome 136+ не принимает `--remote-debugging-port` на профиле по умолчанию |
| Что работает | Отдельный `--user-data-dir` + `--remote-debugging-port`. Вход Google → `accounts.x.ai` прошёл вручную, сессия хранится в профиле |
| Поле промта | `div[role=textbox][aria-label="Ask Grok anything"]`; текст вставляется `Input.insertText` |
| Режим | `button[role=radio]`: «Изображение» (по умолчанию) / «Видео» / «Агент». Простой `click()` работает |
| Параметры видео | «Звук видео» (переключатель), «Разрешение видео» (480p, 720p, 1080p), «Длительность видео» (6s, 10s, 15s), «Соотношение сторон» (Авто, 2:3, 3:2, 1:1, 9:16, 16:9) |
| Как открывать меню параметров | Меню Radix (`menuitemradio`). `el.click()` их **не открывает**; нужны настоящие события мыши `Input.dispatchMouseEvent` по координатам кнопки |
| Отправка | `button[type=submit][aria-label="Отправить"]`, появляется только после ввода текста; работает `click()` |
| После отправки | Адрес меняется на `/imagine/post/<post_id>`; текст «Создаётся N%»; 6-секундное видео 480p готово меньше чем за минуту |
| Признак готовности | Пропал «Создаётся…» и появился `<video>`, чей `src` содержит `post_id`. Адрес: `https://assets.grok.com/users/<uid>/generated/<post_id>/generated_video.mp4?…` |
| Скачивание | `fetch(src, {credentials:'include'})` внутри страницы отдаёт весь файл (HTTP 206, 950 990 байт). Проверено: блоки `ftyp/moov/mdat`, сумма размеров равна размеру файла, `ffprobe`: H.264 464×688, 6,04 с, AAC. Клики по кнопкам скачивания не нужны |
| Фото | Кнопка «Загрузить» открывает панель «Генерации / Загрузки»; внутри неё вторая кнопка «Загрузить» (без `aria-label`) открывает файл-чузер. С `Page.setInterceptFileChooserDialog` системное окно не появляется, приходит `Page.fileChooserOpened` (`mode: selectMultiple`); файл подставляется `DOM.setFileInputFiles` по `backendNodeId` |
| После вставки фото | В композере появляется миниатюра (`img[src^="blob:"]`), кнопка `aria-label="Remove image"` (английская подпись) и «Добавить последний кадр». Кнопка «Соотношение сторон» исчезает: формат берётся из фото |
| Баннер cookie | Есть на странице и не мешает кликам. Согласие не принимается |
| Язык интерфейса | Смешанный: «Remove image» по-английски, остальное по-русски |
| Режим «Изображение» (живой прогон 2026-10-01) | Адрес остаётся `/imagine`, страницы поста нет. Grok выдаёт сетку из 10 и более JPEG 768×1152 прямо на странице как `data:image/jpeg;base64,…` (при «Количество изображений: Авто»), то есть один запрос даёт много картинок и тратит лимит. После отправки композер пуст. Драйвер ждёт, пока сетка перестанет меняться (6 с), сохраняет первую и пишет в примечания «Grok сгенерировал N картинок, сохранена первая». Скачивание не нужно: байты берутся из `data:`-адреса. Возобновить картинку после перезапуска сервера нельзя (нет `post_id`) |

Не проверено пробой: режим «Изображение» (выбор качества, «Количество изображений», получение файла); доступность
720p/1080p/15s на подписке владельца; тексты ошибок (лимит, модерация, сбой генерации); поведение при смене языка.
См. раздел 11.

## 4. Архитектура

Новый драйвер встаёт рядом с `xai` и `dry-run`: интерфейс `Driver` (пять методов), `TaskStore`, модели запросов и
слой MCP-инструментов (`server.py`) не меняются.

Новые модули в `src/grok_imagine_mcp/`:

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `cdp.py` | Минимальный клиент CDP по WebSocket (`aiohttp`): команды с идентификаторами, события в очереди (`wait_event`), `Runtime.evaluate`, `Input.dispatchMouseEvent`/`dispatchKeyEvent`/`insertText`, `Page.*`, `DOM.setFileInputFiles` | `aiohttp` |
| `chrome.py` | Проверка порта отладки; запуск Chrome с профилем и флагами; поиск `chrome.exe`; никогда не вводит пароли и не закрывает окно | `cdp.py`, стандартная библиотека |
| `web_lock.py` | Межпроцессная блокировка на открытом файле (`msvcrt` / `fcntl`), асинхронный захват с таймаутом | стандартная библиотека |
| `media_check.py` | Проверка целостности скачанного mp4 и определение типа картинки | стандартная библиотека |
| `web_options.py` | Сопоставление `VideoRequest`/`ImageRequest` с тем, что умеет интерфейс Grok; отказы `DriverError` | `models.py` |
| `web_types.py` | Общие типы (`BackendState`, `Generated`, `Reporter`, `WebBackend`), чтобы драйвер и backend не импортировали друг друга | `web_options.py` |
| `grok_page.py` | Всё, что знает о вёрстке Grok: таблицы подписей (русские и английские), выбор режима и параметров, вставка фото, отправка, ожидание результата, скачивание. Единственное место, которое ломается при смене сайта | `cdp.py`, `media_check.py` |
| `grok_backend.py` | Связывает Chrome, CDP и `GrokPage` в операции `generate` / `resume` / `state` | `chrome.py`, `grok_page.py` |
| `web_driver.py` | `WebDriver`: пять методов `Driver`, очередь, блокировка, возобновление, тексты ошибок; работает с любым объектом `WebBackend` (в тестах подставной) | `web_options.py`, `web_lock.py`, `TaskStore` |

Изменения в существующем коде: ветка `web` в `build_driver` (`drivers.py`); `describe()` не должен говорить «xAI» для
драйвера `web`; сообщение об отсутствии ключа подсказывает `GROK_DRIVER=web`; явная зависимость `aiohttp>=3.9` в
`pyproject.toml`; раздел «Драйвер web» и предупреждение об условиях xAI в `README.md`.

### Окно Chrome

Сервер сам подключается к окну, если порт отладки отвечает, иначе запускает его (решение владельца):

```
chrome.exe --remote-debugging-port=<GROK_WEB_PORT> --remote-debugging-address=127.0.0.1
           --user-data-dir=<GROK_CHROME_PROFILE> --no-first-run --no-default-browser-check
           --disable-backgrounding-occluded-windows --disable-renderer-backgrounding
           --disable-background-timer-throttling --app=https://grok.com/imagine
```

- Путь к Chrome: `GROK_CHROME_PATH`, иначе стандартные места установки.
- Окно на порту опознаётся по `--user-data-dir` процесса, слушающего порт (Windows, PowerShell; подтверждённый результат
  кэшируется на 10 минут). Чужой браузер на порту: понятная ошибка, в нём ничего не трогается и второе окно не
  запускается. Файл `DevToolsActivePort` для этого не годится: при фиксированном порте Chrome 154 его не пишет
  (проверено живьём). Если процесс опознать нельзя (не Windows), драйвер не мешает.
- Вкладки: драйвер управляет вкладкой `grok.com`, затем вкладкой входа (`accounts.*`), затем пустой; иначе открывает
  свою и закрывает за собой. Чужие вкладки пользователя на `grok.com` не уводятся.
- Сервер окно **не закрывает**: оно остаётся открытым после задачи. Но окно, запущенное сервером, закрывается вместе
  с клиентом, если тот завершает дерево процессов (MCP SDK на Windows кладёт сервер в Job Object с
  `KILL_ON_JOB_CLOSE`); это не обходится, вход хранится в профиле, окно откроется заново.
- Профиль по умолчанию `<GROK_STATE_DIR>\chrome-profile` лежит вне репозитория. Первый вход в аккаунт владелец делает
  руками в этом окне; дальше сессия хранится в профиле.

## 5. Поток одной задачи

Статусы прежние: `pending → done | failed` (`expired` и `recorded_dry_run` драйвером `web` не используются). Внутри
`pending` запись задачи хранит `phase`: `queued`, `submitting`, `generating`, `downloading`; фаза попадает в `message`.

1. `grok_generate_video` / `grok_generate_image`: запрос проходит существующую валидацию моделей, затем проверку
   драйвера (раздел 6). Задача записывается в `TaskStore` со статусом `pending`, фаза `queued`, возвращается `task_id`.
2. Фоновая `asyncio`-задача в процессе сервера берёт **межпроцессную блокировку** `<профиль Chrome>\grok-mcp.lock`
   (общий ресурс клиентов - окно профиля, а не папка состояния)
   (`msvcrt.locking` на Windows, `fcntl.flock` на остальных; освобождается ОС при падении процесса). Блокировка нужна,
   потому что Claude Code и Codex запускают каждый свой процесс сервера, а окно Chrome у них общее. Ожидание очереди
   ограничено `GROK_WEB_QUEUE_TIMEOUT_S` (по умолчанию 3600 с, отсчёт для каждой задачи отдельно).
3. Под блокировкой: подключение к окну (раздел 4), вывод окна на передний план, открытие `/imagine`, проверка входа
   в аккаунт, выбор режима и параметров, вставка фото, вставка текста, отправка.
4. Сразу после отправки `post_id` из адреса `/imagine/post/<post_id>` записывается в задачу; фаза `generating`.
5. Ожидание готовности (признак в разделе 3), не дольше `GROK_WEB_GENERATION_TIMEOUT_S`.
6. Фаза `downloading`: `fetch` в странице, запись во временный файл, проверка сигнатуры и целостности (`ftyp`, `moov`,
   сумма блоков равна размеру), атомарное переименование в `GROK_OUTPUT_DIR`; статус `done`, `output_path`.
7. `grok_task_status(task_id, wait_s)` ждёт изменения статуса до `wait_s` (не более 50 с, как сейчас).

### Возобновление после перезапуска сервера

Клиент перезапускает процесс сервера часто, а задача живёт дольше. Пока исполнитель жив (в любом процессе), он раз
в 15 с пишет `heartbeat_at` в запись задачи (и пока задача ждёт очередь, и пока идёт генерация). `grok_task_status`
для `pending`-задачи без исполнителя в этом процессе смотрит на эту отметку:

- отметка свежая (не старше 90 с): задачу ведёт другой процесс, ничего не делаем;
- отметка протухла и есть `post_id`: запускаем возобновление (блокировка → открыть `/imagine/post/<post_id>` →
  дождаться видео → скачать); страница поста не найдена или с ошибкой → `failed`;
- отметка протухла и `post_id` нет (прервана до отправки, либо это картинка): `failed` с текстом «задача прервана:
  сервер был перезапущен до получения результата; запустите её заново».

Порог не зависит от длины очереди: пакет из многих роликов не ломается, а брошенная задача признаётся такой
через 90 с, а не через 20 минут. Если возобновляющий исполнитель не дождался блокировки, задача остаётся `pending`.

**Потеря связи с окном** (окно закрыли, Chrome упал или обновляется). Если `post_id` уже записан, задача остаётся
`pending` с протухшей отметкой и дожимается следующим `grok_task_status` (с новым окном); не больше 3 обрывов
подряд (`resume_attempts`), затем `failed`. Если запрос ещё не ушёл, задача `failed` («связь с окном Chrome
потеряна»): повторять нельзя, чтобы не потратить лимит дважды.

Поле `submitted` в записи задачи остаётся `false`, пока задача не отправлена в Grok (пока нет `post_id`), и становится
`true` с моментом отправки. Так «задача в очереди» не выдаётся за «отправлено».

## 6. Сопоставление параметров и проверки

Модели `VideoRequest`/`ImageRequest` общие с драйвером `xai`, поэтому допустимое для интерфейса Grok проверяет сам
драйвер и отклоняет остальное понятным `DriverError` с перечнем допустимого. Молча подгонять значения нельзя.

| Поле | Поведение драйвера `web` |
|---|---|
| `prompt` | Вставляется в поле промта |
| `image_path` (видео) | Проходит существующую проверку `_check_image` (абсолютный путь, тип, размер ≤ 10 МБ); загружается через перехваченный файл-чузер |
| `duration_s` | Допустимо 6, 10, 15; иное — ошибка. `None` — не трогать |
| `resolution` | Допустимо 480p, 720p, 1080p. Если пункт меню недоступен на подписке — ошибка с текстом со страницы |
| `aspect_ratio` | Допустимо 2:3, 3:2, 1:1, 9:16, 16:9; 4:3 и 3:4 — ошибка. **С `image_path` игнорируется**: формат берётся из фото, о чём сообщается в `message` |
| `generate_audio` | Приводит переключатель «Звук видео» к нужному состоянию |
| `model` | В `web` не применяется; сообщается в `message` |
| Картинки: `aspect_ratio`, `resolution`, `model` | Применимость к интерфейсу Grok не проверена пробой; правила фиксируются в плане после живой пробы режима «Изображение» (раздел 11) |

После каждого выбора значение перечитывается со страницы (для параметров меню - текст кнопки, для звука -
состояние переключателя). Если Grok значение не применил (промах клика, перекрытие, сдвиг вёрстки), генерация не
запускается: иначе вышло бы видео с настройками по умолчанию, выданное за заказанное.

## 7. Ошибки

Все ожидаемые сбои — `DriverError` с текстом для модели и пользователя; задача при этом `failed`, если уже была создана.

- Нет входа в аккаунт (адрес ушёл на `accounts.x.ai`/страницу входа): «войдите в Grok в окне Chrome (профиль …) и
  повторите». Драйвер **никогда** не вводит логин, пароль, коды и не обходит капчу.
- Не найден элемент интерфейса: ошибка со списком найденных подписей, чтобы дрейф вёрстки диагностировался сразу.
- Диалог поверх страницы (лимит, апгрейд, модерация): задача `failed` с текстом диалога. Драйвер не нажимает в
  незнакомых диалогах ничего, включая баннер cookie и согласия.
- Таймаут ожидания генерации или очереди: `failed` с соответствующим текстом.
- Окно Chrome скрыто (закрыто другими окнами, свёрнуто): в скрытом окне Chrome не рисует кадры, меню не
  открываются. Запуск идёт с `--disable-features=CalculateNativeWinOcclusion`, свёрнутое окно разворачивается, а
  ошибка называет причину («окно Chrome скрыто»), а не «интерфейс изменился».
- Chrome не найден или порт занят чужим процессом: ошибка с подсказкой `GROK_CHROME_PATH` / `GROK_WEB_PORT`.

`grok_status`: сообщает, отвечает ли порт и выполнен ли вход, **но окно не запускает** и страницы не открывает. В
`detail` напоминает, что автоматизация веб-интерфейса подписки может не соответствовать условиям xAI.

## 8. Безопасность и приватность

- Порт отладки слушает только `127.0.0.1`, но пока окно открыто, любая локальная программа может управлять сессией
  Grok из этого профиля. Это свойство CDP, оно документируется в README.
- Профиль содержит сессию входа; лежит вне репозитория (`<GROK_STATE_DIR>\chrome-profile`), в git не попадает.
- Драйвер не читает Библиотеку, историю и названия чатов пользователя; обращается только к элементам композера и
  страницы результата.
- Загружаются только файлы, которые модель передала как `image_path` и которые прошли `_check_image`.
- Условия xAI: автоматизация веб-интерфейса подписки может их нарушать, а смена вёрстки ломает драйвер. Это уже
  указано в README для запасного пути и повторяется в разделе «Драйвер web».

## 9. Настройка

`GROK_DRIVER=web` можно положить в `~/.grok_imagine_mcp/.env`: тогда он действует на все клиенты, и серверы, уже
зарегистрированные в Claude Code (`grok-imagine-xai`) и Codex (`grok-imagine`), перерегистрировать не нужно.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `GROK_DRIVER` | `xai` | `web` включает этот драйвер |
| `GROK_WEB_PORT` | `9340` | Порт отладки окна Chrome |
| `GROK_CHROME_PROFILE` | `<GROK_STATE_DIR>\chrome-profile` | Профиль Chrome для Grok |
| `GROK_CHROME_PATH` | автопоиск | Путь к `chrome.exe` |
| `GROK_WEB_GENERATION_TIMEOUT_S` | `900` | Предел ожидания одной генерации |
| `GROK_WEB_QUEUE_TIMEOUT_S` | `3600` | Предел ожидания очереди за блокировкой (для каждой задачи отдельно) |

## 10. Тестирование

Тесты в стиле существующих (`pytest`, `tmp_path`, подставные реализации, без реального API и без Chrome).

- **Логика драйвера** на подставной реализации страницы (`Protocol` поверх `grok_page`): сопоставление параметров и
  отказы, переходы статусов и фаз, блокировка между двумя драйверами, возобновление по `post_id`, задача без `post_id`,
  «нужен вход», диалог поверх страницы, ошибка с перечнем подписей, проверка целостности mp4.
- **`cdp.py`** против локального WebSocket-сервера на `aiohttp`: корреляция команд и ответов, события, пришедшие между
  ответом и ожиданием, ошибки протокола.
- **`chrome.py`**: разбор результата проверки порта и сборка командной строки без запуска процесса.
- **Живой тест** (`@pytest.mark.live`, пропускается, пока не задан `GROK_WEB_LIVE=1`): одна генерация 6 с / 480p по
  тексту и одна по синтетической картинке; проверка целостности mp4. JS-фрагменты внутри страницы покрываются только им.
- Из пробы: меню Radix открываются только настоящей мышью; обычные кнопки принимают `click()`; файл-чузер нужно
  перехватывать до клика; нельзя импортировать скрипт с запуском на уровне модуля (была ошибка двойного клика).

## 11. Открытые вопросы (закрываются живой пробой в начале реализации)

1. Режим «Изображение»: закрыт частично живым прогоном (раздел 3): результат приходит сеткой `data:`-адресов,
   сохраняется первая. Остаётся открытым: переключатель «Скорость» / «Качество 2.0» и кнопка «Количество изображений»
   остаются по умолчанию, драйвер их не задаёт; уменьшение числа картинок (чтобы не тратить лимит) и сопоставление
   `ImageRequest.model`/`resolution` с этими контролами не сделаны.
2. Доступны ли 720p, 1080p и 15s на подписке владельца и как выглядит отказ.
3. Тексты и разметка ошибок: лимит, модерация, сбой генерации.
4. Поведение при другом языке интерфейса; нужен ли `--lang` для профиля.
5. Сколько генераций Grok допускает одновременно (влияет только на будущую параллельность).
